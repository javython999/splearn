# 포트(port)

* 애플리케이션이 외부 세계와 의도(intention)를 가지고 상호작용 하는 아이디어를 캡처한 것
* 단순히 데이터를 주고 받는 것이 아니라, 명확한 목적과 방향을 가지고 외부와 연결된다.

소통 의도를 기준으로 애플리케이션 포트 구성
* 어댑터와 다른 애플리케이션 컴포넌트에서 필요한 인터페이스에만 의존할 수 있다.

# 애플리케이션 컴포넌트

## UML 컴포넌트
* 시스템을 구성하는 __독립적이고 교체 가능한 모듈__(Unit)
* 내부 구현을 __캡슐화__ 하고 외부에는 __제공 인터페이스(Provided Interface)__ 와 __요구 인터페이스(Required Interface)__ 만 노출
* 동일한 인터페이스를 제공하면 __다른 구현체로 교체__ 가능

#### 명확한 인터페이스를 통해 협력하며 독립적으로 교체 가능한 시스템의 구성 단위

## 헥사고날 아키텍처 컴포넌트

* __UML의 컴포넌트__ 개념과 객체 지향의 __전략(Strategy)패턴__ 이 결합된 형태로 정의
* 외부에 기능을 제공하는 __드라이빙포트/제공 인터페이스__
* 외부에 기능을 요구하는 __드리븐 포트/요구 인터페이스__
* 외부 기술은 __어댑터를 통해 구현된 전략 패턴__ 으로 __런타임__ 에 애플리케이션에 주입

## 헥사고날 아키텐처의 중첩이 가능한가?
* UML 컴포넌트의 철학을 __애플리케이션 아키텍처 수준__ 으로 끌어올린 특수한 적용 사례
* 포트와 어댑터 패턴의 핵심의도는 DB나 UI, 외부 API와 같은 __변경 가능한 기술의 변화__ 로부터 __도메인의 로직을 보호__ 하는 것
* 헥사고날 아키텍처는 __중첩 구조를 명시적으로 부정__
* 내부 컴포넌트의 외부 기술에 대한 __어댑터는 반드시 애플리케이션 외부에 위치__ 하고 __런타임에 주입__ 받도록 해야함

# 애그리거트 사이의 연결
* 애그리거트는 __데이터 변경의 목적__ 을 위해 __하나의 단위로 최급__ 되는 __연관된 객체들의 집합__ 이다.
* 경계 내의 어떤 변경 사항이 있을 때 전체 애그리거트의 모든 __불변식이 충족__ 되어야 한다.
* __리포지토리__ 를 통해서 __애그리거트 루트만__ 직접 얻을 수 있다.
* 애그리거트 내부의 객체는 __다른 애그리거트의 루트에 대한 참조__ 를 가질 수 있다.(Eric Evans)
* 다른 애그리거트의 루트에 대한 직접 참조가 아니라 __식별자(ID)로만 해야 한다.__ 는 주장도 있다.(Vaughn Vernon)

## 애그리거트 간의 직접 참조와 식별자 참조
```java
public class Instructor {
    @OneToOne
    private Member member;
}
```
```java
public class Instructor {
    private Long memberId;
}
```

## DDD를 만든 에릭 에반스가 객체 참조를 설계의 유효한 선택지로 본 이유
* 객체지향 패러다임과 모델의 자연스러운 매핑
* 연관관계의 응집도(cohesiveness)와 표현력 - 탐색과 검색을 적절히 조합
* 데이터베이스 중심 설계로의 변질 방지

## 도메인 애그리거트와 애플리케이션 컴포넌트의 연결
* 애그리거트 사이의 관계는 __직접 참조로 시작__ 한다.
* 단, __변경 기능은 참조를 통해서 사용하지 않도록__ 한다.
* 애그리거트에 대한 __변경은 해당 애플리케이션 컴포넌트를 통해서__ 진행한다.
* 애플리케이션 컴포넌트의 __인터페이스를 통해서 애그리거트를 전달__ 할 때는 __식별자를 사용__ 한다.
* 이 정책이 바르게 적용됐는지 __ArchUnit을 통해 검증__ 한다.
